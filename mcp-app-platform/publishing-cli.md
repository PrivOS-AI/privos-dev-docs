# Publishing an MCP App — the `privos-app` CLI

`privos-app publish` is the supported way to publish an MCP app version to the
PrivOS Marketplace. It replaces the old hand-driven `.mjs` scripts and manual
Portal calls: one command runs **package → lint → authorize → upload → version →
submit** from the app folder. Listing content (categories, screenshots, legal
URLs, pricing, Stripe Connect) stays in the web Creator Studio; the CLI only
publishes the code identity declared in `privos-app.json`.

The CLI ships in `@privos_ai/app-server` (bin `privos-app`, plus the
`privos-app-lint` alias). It is **always on** in production — there is no feature
flag to enable.

## Install

`@privos_ai/app-server` is already a dependency of a scaffolded app, so its
`privos-app` bin runs through the app's npm scripts without extra install. Apps
generated by `create-privos-mcp-app` (≥ 0.4.0) ship a `publish:marketplace`
script and a `privos-app-publish` agent skill under `.claude/skills/`.

```bash
npm run publish:marketplace -- --help
# outside an app, name the scoped package explicitly
npx -p @privos_ai/app-server privos-app --help
```

The unscoped npm name `privos-app` is not this package, so never hand it to a
package runner on its own.

## Two authorization modes

Both terminate in the **same scoped grant** the Portal honors on the publish
routes — never a raw browser session.

### 1. Browser approval (default, interactive)

```bash
cd my-mcp-app
npm run publish:marketplace
#  ✔ manifest privos-app.json valid
#  ✔ archive dist-source/my-app-1.4.0.zip (2.1 MB, sha256 …)
#  → Approve this publish in your browser:
#      https://client.privos.io/marketplace/publish?user_code=WDJB-MJHTK
#    (waiting… expires in 15 min)
#  ✔ approved by dev@example.com → listing my-app
#  ✔ uploaded · version 1.4.0 created · submitted
#  → status: PREFLIGHT_PENDING  (follow up in Creator Studio)
```

The CLI opens an OAuth-device-style *publish authorization* (device code + user
code) naming the manifest, semver, and archive sha256. The developer opens the
printed URL on `client.privos.io`, logs in, sees which listing/version will be
published and who requested it, and approves. The CLI polls and receives a
**publish grant** bound to that one archive + listing. The approval page shows
only server-derived facts and a warning — there is no CLI-supplied permission
diff (it would be spoofable). Only the creator who owns the listing can approve.

### 2. Publisher token (non-interactive / CI)

```bash
PRIVOS_PUBLISHER_TOKEN=pvp_… npm run publish:marketplace -- --yes
```

A long-lived `MarketplacePublisherToken` (`pvp_…`, hashed at rest, prefix shown,
scoped to the creator or to named listings, ≤ 90-day expiry, revocable). It
auto-approves **only** a listing whose first version was already approved in the
browser (a token against an unbound listing → `409 LISTING_NOT_BOUND`; the first
publish of any listing must be interactive).

Create / rotate / revoke tokens in Creator Studio → Publisher tokens. Each is a
**step-up action**: an email code or magic link, **plus TOTP when the account has
2FA**. The token secret is shown once; store it in an environment/CI secret,
never in chat, a file, or a command argument.

## Command reference

`privos-app publish [options]`

| Option | Meaning |
|---|---|
| `--dry-run` | Package + lint only; print git rev + archive sha256; no authorize/upload |
| `--yes` | Skip the interactive TTY confirmation (for CI) |
| `--listing <slug>` | Resolve the listing explicitly when the manifest name is ambiguous |
| `--changelog <text>` / `--changelog-file <path>` | Version changelog |
| `--allow-dirty` | Package an uncommitted working tree (default refuses a dirty tree) |
| `--machine-label <text>` | Label shown on the approval page (never the hostname by default) |
| `--portal <origin>` | Portal origin (default `https://portal.privos.io`; or `PRIVOS_PORTAL_ORIGIN`) |
| `--token-stdin` | Read `PRIVOS_PUBLISHER_TOKEN` from stdin instead of the environment |
| `--open` | Open the approval URL in a browser (interactive mode) |
| `--json` | Emit one NDJSON event per step on stdout |
| `--cwd <path>` | Run against another directory |

`privos-app lint [manifestPath]` — structural manifest lint (identical to the
`privos-app-lint` alias). Note: the CLI's structural manifest hash is **not** the
Portal's canonical digest and is never sent; the Portal computes and returns the
digest on upload completion.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | Submitted (or a benign non-blocking status) |
| 2 | Blocked by policy (manifest invalid, dirty tree, denied archive path, `VERSION_SEMVER_EXISTS`, `LISTING_CONTENT_INCOMPLETE`, `PUBLISHER_NOT_ENABLED`, preflight failed, `LISTING_NOT_BOUND`/`LISTING_UNRESOLVED`) |
| 3 | Authorization denied / expired / consumed, or publisher token revoked/expired/invalid |
| 4 | Network or Portal error |
| 5 | Usage error (bad flags, cancelled prompt, not a git repository) |

## Packaging rules

`publish` packages with `git archive` (parity with the legacy
`scripts/package-source.sh`, retained only for parity checks): it refuses a dirty
tree unless `--allow-dirty`, scans for credential files, requires root entries
`privos-app.json` + `Dockerfile` (an INSTANT app needs no `Dockerfile` from SDK
0.12.1 on), and rejects `.env*`, `node_modules`, `.git`,
`..`, > 20k entries, > 50 MB/file, > 200 MB total. The entry list is read from
the produced zip's central directory. Bump `version` in **both** `privos-app.json`
and `package.json` (they must match, else `MANIFEST_IDENTITY_MISMATCH`).

## Security model

- Every credential the CLI holds is either a **60-minute grant** bound to one
  archive + listing, or a revocable, hashed publisher token limited to the
  publish routes — never a browser session.
- The grant is `pvg_<authorizationId>.<HMAC>`; nothing secret is stored server
  side. It enforces `archiveSha256`, `manifest.name === listing.manifestName`,
  and `manifest.version === grant.semver` at upload completion
  (`409 PUBLISH_GRANT_MISMATCH`), and is single-use for submit.
- Publisher tokens and grants reach **only** the publish route allowlist; a token
  cannot manage tokens, edit listing content, or touch Stripe Connect
  (`403 PUBLISHER_TOKEN_SCOPE` / `PUBLISHER_TOKEN_NOT_ALLOWED`).
- Re-publishing the same semver fails fast with `VERSION_SEMVER_EXISTS` (exit 2).

## The UI bundle

A version whose manifest declares a UI doesn't reach `PUBLISHED` without one:
after admin approval, the build node runs `privos-app bundle-ui` over your
built UI (`ui.distDir`) and the Portal signs the resulting bundle's digest.
The installing Hub verifies that digest before the app ever goes active. See
[The signed UI bundle](./ui-bundle.md) for the full flow, the refusal codes
(`MARKETPLACE_V3_UI_BUNDLE_MISSING`, `UI_BUNDLE_INGEST_FAILED:<code>`, …), and why an unchanged
UI reuses its already-published bundle.

## INSTANT apps

An INSTANT app (`executionMode: "INSTANT"`, no server, no `Dockerfile`) goes
through this same pipeline with the Dockerfile requirement skipped — but only
once the listing's `supportedExecutionModes` includes `"INSTANT"` (Creator
Studio has no editor for this yet; ask a marketplace admin). Run
`privos-app publish --dry-run` before a real publish: the plain `lint --publish`
check does not catch every manifest problem `publish` itself rejects (e.g.
duplicate permission `feature` ids). See [INSTANT apps](./instant-apps.md) for
the full manifest contract and publish checklist.

## After submit

The CLI has no `status`/`whoami` command. Review progress
(`PREFLIGHT_PENDING` → `SCAN` → `AI_REVIEW` → human `APPROVE` → build) is followed
in Creator Studio on `client.privos.io`.

## Who can publish

Marketplace publishing is open to enabled creators only. For anyone else the
Portal refuses the source upload with `403 PUBLISHER_NOT_ENABLED` before it
stores anything, so no version is created and the publish grant is not used up.
The CLI (`@privos_ai/app-server` 0.12.3 or later) prints the Portal's message and
exits 2. The app can still run in your own workspace as a Standalone Relay app.

A first version of a listing whose content is still incomplete is refused at
version creation with `409 LISTING_CONTENT_INCOMPLETE`; the message lists what
is missing (exit 2). `PREFLIGHT_BLOCKED_INFRA` after submit is an
infrastructure state only.

## Portal endpoints (reference)

Mounted under `/api/cloud/marketplace`:

- `POST /publish-authorizations` — anonymous create (or `pvp_` for CI auto-approve) → `{ deviceCode, userCode, verificationUrl, expiresIn: 900, interval: 5 }`
- `GET /publish-authorizations/:userCode` — approval-page data (session auth)
- `POST /publish-authorizations/:userCode` — `{ decision: 'approve'|'deny', listingId? }` (session auth, must own the listing's creator)
- `POST /publish-authorizations/token` — `{ deviceCode }` poll, RFC 8628 semantics (`slow_down`)
- `GET/POST /creator/tokens*` — publisher token management (session auth + step-up)
